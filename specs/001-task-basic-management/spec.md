**状態**: Draft

## Clarifications

### Session 2026-05-09

- Q: 詳細・更新・削除で、taskId が別 userId に属する場合はどう扱いますか？ → A: 一覧・詳細・更新・削除のすべてで userId スコープを必須にし、別 userId の taskId は存在しないものとして共通エラーを返す
- Q: 作成時点・更新時点のタイムゾーンはどう扱いますか？ → A: API利用者へ返す時刻は JST (`Asia/Tokyo`, UTC+09:00) の ISO-8601 オフセット付き文字列とし、サーバのデフォルトタイムゾーンには依存しない

## ユーザーシナリオとテスト *(必須)*

### ユーザーストーリー 1 - 自分のタスクを登録する (Priority: P1)

個人ユーザーは、取り組むべき作業を忘れないように、自分のタスクとしてタイトル、説明、ステータスを登録できる。

**この優先度の理由**: タスク管理の起点であり、登録できなければ一覧、詳細、更新、削除の価値を提供できないため。

**独立テスト**: userId とタスク内容を指定して登録し、登録したタスクが同じ userId のタスクとして取得可能になることを確認する。

**受け入れシナリオ**:

1. **Given** userId と有効なタイトル、説明、ステータスがある, **When** ユーザーがタスクを登録する, **Then** 登録済みタスクとして識別でき、登録内容を取得できる
2. **Given** ステータスが `TODO`, `DOING`, `DONE` 以外である, **When** ユーザーがタスクを登録する, **Then** タスクは登録されず、共通フォーマットのエラーが返る

---

### ユーザーストーリー 2 - 自分のタスクを確認する (Priority: P2)

個人ユーザーは、自分のタスクだけを一覧で確認し、必要なタスクの詳細を見て登録内容や進捗を把握できる。

**この優先度の理由**: 登録したタスクを整理し、抜け漏れや優先順位を判断するための中心的な利用行動であるため。

**独立テスト**: 複数 userId のタスクを用意し、指定した userId の未削除タスクのみが一覧に返り、対象タスクの詳細が登録内容と一致することを確認する。

**受け入れシナリオ**:

1. **Given** 複数 userId のタスクが登録されている, **When** ある userId のタスク一覧を確認する, **Then** その userId の未削除タスクのみが返る
2. **Given** 登録済みで未削除のタスクがある, **When** そのタスクの詳細を確認する, **Then** タイトル、説明、ステータス、userId が登録内容と一致する
3. **Given** 存在しない、または論理削除済みのタスクIDがある, **When** そのタスクの詳細を確認する, **Then** 共通フォーマットのエラーが返る

---

### ユーザーストーリー 3 - タスクの内容と進捗を更新する (Priority: P3)

個人ユーザーは、タスクの内容や進み具合が変わったときに、タイトル、説明、ステータスを更新できる。

**この優先度の理由**: タスクの状態を最新に保つことで、進捗把握の正確性が上がるため。

**独立テスト**: 登録済みタスクのタイトル、説明、ステータスを更新し、その後の取得結果に更新内容が反映されることを確認する。

**受け入れシナリオ**:

1. **Given** 登録済みで未削除のタスクがある, **When** ユーザーがタイトル、説明、ステータスを更新する, **Then** 以後の取得結果に更新内容が反映される
2. **Given** 更新後ステータスが `TODO`, `DOING`, `DONE` 以外である, **When** ユーザーがタスクを更新する, **Then** 更新は反映されず、共通フォーマットのエラーが返る
3. **Given** 存在しない、または論理削除済みのタスクIDがある, **When** ユーザーがタスクを更新する, **Then** 共通フォーマットのエラーが返る

---

### ユーザーストーリー 4 - 不要なタスクを取り除く (Priority: P4)

個人ユーザーは、不要になったタスクを通常の一覧や詳細確認から取り除き、現在扱うタスクだけを見られる。

**この優先度の理由**: 不要なタスクが残り続けると、整理と進捗把握の妨げになるため。

**独立テスト**: 登録済みタスクを削除し、その後の一覧と詳細確認で取得できないことを確認する。

**受け入れシナリオ**:

1. **Given** 登録済みで未削除のタスクがある, **When** ユーザーがタスクを削除する, **Then** そのタスクは論理削除済みとなり、一覧と詳細確認から取得できない
2. **Given** 存在しないタスクIDがある, **When** ユーザーがタスクを削除する, **Then** 共通フォーマットのエラーが返る

### エッジケース

- userId が異なるタスクは、一覧・詳細・更新・削除のすべてで対象に含めず、存在しないタスクと同じ共通フォーマットのエラーとして扱う。
- 論理削除済みタスクは、一覧、詳細、更新、削除の通常操作で有効なタスクとして扱わない。
- `TODO`, `DOING`, `DONE` 以外のステータスは、登録と更新のどちらでも受け付けない。
- userId、タイトル、ステータスのいずれかが不足している、または入力形式が不正な場合、タスク内容は保存・更新されず、共通フォーマットのエラーが返る。
- エラー時の応答には `code` と `message` を必ず含め、必要に応じて `details` を含める。アプリケーション独自のエラーコードは追加しない。
- サーバのデフォルトタイムゾーンが JST 以外でも、作成時点・更新時点の API 表現は JST (`+09:00`) として一貫させる。

## 要件 *(必須)*

### 機能要件

- **FR-001**: システムは、外部から与えられた userId に紐づけてタスクを登録できなければならない。
- **FR-002**: システムは、タスク登録時にタイトル、任意の説明、ステータスを受け取れるようにしなければならない。
- **FR-003**: システムは、タスクステータスを `TODO`, `DOING`, `DONE` のみに制限しなければならない。
- **FR-004**: システムは、指定された userId の未削除タスクのみを一覧として返せなければならない。
- **FR-005**: システムは、他の userId に紐づくタスクを一覧結果へ含めてはならない。
- **FR-006**: システムは、指定された userId に紐づく登録済みで未削除のタスクについて、登録内容と一致する詳細を返せなければならない。
- **FR-007**: システムは、指定された userId に紐づく登録済みで未削除のタスクについて、タイトル、説明、ステータスを更新できなければならない。
- **FR-008**: システムは、指定された userId に紐づくタスクを物理的に失わせるのではなく、通常の一覧・詳細対象から除外される削除済み状態にできなければならない。
- **FR-009**: システムは、存在しないタスクID、指定された userId に紐づかないタスクID、論理削除済みタスク、不正な入力を指定された場合にエラーを返さなければならない。
- **FR-010**: システムは、エラーを `code`, `message`, 任意の `details` を持つ共通フォーマットで返さなければならない。
- **FR-011**: システムは、アプリケーション独自のエラーコードを持ってはならない。
- **FR-012**: システムは、この機能範囲では認証を導入せず、userId は外部から与えられる識別子として扱わなければならない。
- **FR-013**: システムは、タスクの userId、タイトル、説明、ステータス、削除状態、作成時点、更新時点を保持できなければならない。
- **FR-014**: システムは、登録、一覧、詳細、更新、削除、バリデーション、共通エラーの完了条件を確認できるテストを備えなければならない。
- **FR-015**: システムは、userId、タイトル、ステータスを必須入力として検証し、説明は任意入力として扱わなければならない。
- **FR-016**: システムは、作成時点・更新時点を API 応答では JST (`Asia/Tokyo`, UTC+09:00) の ISO-8601 オフセット付き文字列として返し、サーバのデフォルトタイムゾーンに依存してはならない。

### 主要エンティティ *(データを扱う機能の場合に含める)*

- **Task**: 個人ユーザーが管理する作業項目。userId、タイトル、説明、ステータス、削除状態、作成時点、更新時点を持つ。
- **TaskStatus**: タスクの進捗状態。許可値は `TODO`, `DOING`, `DONE` のみ。
- **ErrorResponse**: エラー発生時に利用者へ返す共通情報。`code`, `message`, 任意の `details` を持ち、アプリケーション独自のエラーコードは持たない。

## プロジェクト検証 *(必須)*

- **仕様参照**: `.specify/memory/constitution.md`、ルート `AGENTS.md`、Jira `SCRUM-6`、およびサブタスク `SCRUM-16` から `SCRUM-23` を確認済み。この仕様を今回のタスク基本管理の唯一の正として扱う。
- **API契約への影響**: タスク基本管理リソースとして `/users/{userId}/tasks` と `/users/{userId}/tasks/{taskId}` を対象にする。URLパスには動詞を含めず、userId 単位でタスクを扱う。
- **Taskドメインルール**: Task.status は `TODO`, `DOING`, `DONE` のみに制限する。削除は論理削除とし、Task は userId と作成・更新時点を保持する。API 応答の時刻は JST (`Asia/Tokyo`, UTC+09:00) とし、サーバのデフォルトタイムゾーンに依存させない。
- **モデル境界**: バックエンドではドメインモデルと入出力モデルを混在させない。フロントエンド接続はこのバックエンドAPI契約が固まった後に扱う。
- **バリデーションとエラー**: 不正入力、存在しないタスクID、論理削除済みタスク、不正ステータスはエラーとする。エラーは `code`, `message`, 任意の `details` を持つ共通フォーマットに統一し、アプリケーション独自のエラーコードは追加しない。
- **検証計画**: サブタスク単位で、永続化モデル、登録、一覧、詳細、更新、論理削除、入力バリデーション、共通エラー、主要な正常系・異常系テストを確認する。
- **出力言語**: 仕様本文は日本語で作成し、ステータス値、フィールド名、APIパス、Jira issue key などの識別子のみ原文表記を維持する。

## 成功基準 *(必須)*

### 測定可能な成果

- **SC-001**: 有効な入力でタスクを登録した場合、100%の受け入れシナリオで登録内容と一致するタスクを取得できる。
- **SC-002**: 複数 userId のタスクが混在していても、一覧確認では100%の受け入れシナリオで指定 userId の未削除タスクのみが返る。
- **SC-003**: タスクのタイトル、説明、ステータスを更新した場合、100%の受け入れシナリオで次回確認時に更新内容が反映されている。
- **SC-004**: 論理削除したタスクは、100%の受け入れシナリオで一覧と詳細確認のどちらからも取得できない。
- **SC-005**: 不正ステータス、存在しないタスクID、論理削除済みタスク、不正入力の各エラーシナリオで、100%の受け入れシナリオが `code` と `message` を含む共通フォーマットを返す。
- **SC-006**: サブタスク `SCRUM-16` から `SCRUM-23` の完了条件がすべて満たされたとき、タスク基本管理の主要操作を登録から削除まで一連で確認できる。
- **SC-007**: サーバのデフォルトタイムゾーンに依存せず、作成時点・更新時点の API 応答が100%の確認ケースで JST (`+09:00`) の ISO-8601 形式になる。

## 前提

- 対象ユーザーは、個人利用として自分のタスクを管理するユーザーである。
- 今回の対象はバックエンド側のタスク基本管理であり、フロントエンド接続は後続の機能サイクルで扱う。
- 認証はこの機能範囲に含めず、userId は外部から与えられる。
- userId、タイトル、ステータスは必須入力として扱い、説明はタスクの補足情報として任意入力で扱う。
- 作成時点・更新時点の業務タイムゾーンは JST (`Asia/Tokyo`) として扱う。
- 削除済みタスクの復元、優先度、期限、並び替え、検索、担当者管理は今回の範囲に含めない。
